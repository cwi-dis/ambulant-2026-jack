# Players, back-ends and the Python bridge (assessment, 2026-10-01)

Written in answer to two questions from Jack, after the 2.6 reference
player turned out to run. Complements the cold-pass
[architecture.md](architecture.md), which is left unchanged.

## Three layers, not "the SDL window"

**Jack's starting picture:** "the core is basically the SDL window, plus
the plugin mechanism and some plugins; the Cocoa player is a little skin
around all of this."

**Correction:** there are three layers.

1. **Core** (`libambulant`: `lib`, `common`, `smil2`, `net`):
   platform-independent parsing, SMIL timing, layout, datasources. Draws
   nothing.
2. **Renderer back-end per toolkit** (`gui/cg`, `gui/SDL`, `gui/gtk`,
   `gui/d2`): windows, surfaces, and image/text/video/fill/transition
   renderers. **SDL is one back-end, a peer of the others.** 4.5–6k lines
   each.
3. **Player**: the skin (menus, document window, preferences) that plugs a
   back-end into the core. 2–3k lines each.

The Cocoa player uses the `cg` back-end; SDL is only used for audio output.

## Do the players share a structure? (Jack's question 1)

Yes. Every player:

1. creates a `gui_player` subclass, or something in that role;
2. registers its back-end's renderer factories and the datasource factories;
3. loads the plugins, parses the document, creates the SMIL player;
4. forwards menu, mouse and window events.

| Player | Skin | Renderers | Audio/video | Skin size |
|--------|------|-----------|-------------|----------:|
| `player_macosx` | Cocoa, Objective-C++ | `cg` | ffmpeg + SDL audio | 2.2k |
| `player_iphone` | UIKit | `cg` (shared with macOS) | ffmpeg + SDL audio | 3.6k |
| `player_gtk` | GTK | `gtk` | ffmpeg + SDL audio | 3.0k |
| `player_sdl` | minimal: a window, no menus | `SDL` | ffmpeg + SDL audio | 1.6k |
| `player_mfc` | MFC | `d2` (Direct2D) | **DirectShow** (ffmpeg optional) | 3.0k |
| `npambulant` / `ieambulant` | NPAPI / ActiveX glue | `cg` or `d2` | as on their platform | 3.3k / 0.9k |

Nothing is essentially different. **Windows is the outlier**: media
normally goes through DirectShow instead of ffmpeg/SDL, and the "mainloop"
role sits mostly in the back-end (`d2_player`) rather than in the skin. (The
2007-era design text already calls the Windows player "an exception" to the
mainloop pattern.)

## The Python bridge (Jack's question 2)

*To be complemented by Jack's own account of the effort that went into it.*

- **`src/pyambulant`** is a **two-way bridge**: Python can drive
  Ambulant, and Python classes can implement C++ interfaces (renderers,
  embedders, state engines, …). It is **generated by bgen** from the C++
  headers: `ambulantmodule.cpp` (19k lines) and `ambulantinterface.cpp`
  (9.5k lines), from about 1k lines of generator configuration
  (`ambulantscan.py`, `ambulantsupport.py`, `genobjects.py`, bgen C++
  extensions). 290 commits 2005–2015, 249 by Jack.
- **Uses:**
  - *Embedding:* `pyambulant/player_pygtk` (Rodrigo Laiola, 2007);
    `pyambulant/test/nogui_player.py` (a headless player in Python).
  - *Extending,* through `src/plugins/pythonplugin.cpp`:
    - `pyamplugin_state`: SMIL State in Python
    - `pyamplugin_timesync`: clock synchronisation
    - `pyamplugin_playable`: renderers in Python
    - `pyamplugin_trace`: a tracer with its own web server and a D3.js
      timeline visualisation
    - `sandbox/ambulant-recorder-plugin/src/pyamplugin_recorder.py`
  - *Testing:* the nightly reference traces (`tests/nightly/*-reference.txt`)
    were produced by `pyamplugin_trace`. **The existing regression test
    depends on Python.**
- **Why:** the design goal of a research system with replaceable
  components, and "the whole external API also available in Python, to
  facilitate rapid prototyping" (`Documentation/Design/text/overall.txt`).
- **Revival implications:**
  - Not needed for the minimal product.
  - On the path to testing with the old reference traces (unless a C++
    tracer replaces it).
  - Reviving it means porting bgen and its output to Python 3, or replacing
    the generator, e.g. with pybind11 or nanobind. To be decided after
    Jack's account.
- **In the 2.6 binary:** the Python plugin is present but silently not
  loaded, since it links against the system Python 2.7 framework, which no
  longer exists.
