# Rot audit (cold pass)

What Ambulant depends on, and what has happened to each dependency since the
code was last touched (2015/2016). The status of the outside world comes from
Claude's general knowledge, not from fresh web lookups: *(knowledge)*. Counts
are from `git grep` over `src` and `include`.

Ratings: **ok** = probably still fine · **port** = API changes, mechanical
but real work · **replace** = gone, needs a different technology · **drop** =
the target platform itself is gone.

## Platform APIs

| API | Where | Status | Rating |
|-----|-------|--------|--------|
| NPAPI | `src/npambulant` (~170 hits), plus bits in `gui/cg` | removed from every browser by 2017 | **drop** |
| ActiveX / ATL (Internet Explorer) | `src/ieambulant` | IE retired | **drop** |
| QTKit | `player_macosx` Makefile links it, `QTMovieView` in a nib | QTKit is removed from current macOS | **port** (small: probably dead references, the video path appears to be `cg_avfoundation_video.mm`) |
| ATSUI | `gui/cg/atsui_text.mm` | deprecated, replaced by CoreText long ago. The file is still in the autotools and Xcode builds, but nothing else in `gui/cg` refers to `atsui_text_renderer` *(code)*, so it's probably dead code | **drop** |
| Carbon headers | 3 files in `npambulant` | goes away with npambulant | **drop** |
| Cocoa / CoreGraphics / AVFoundation | `gui/cg`, `player_macosx` | still current, but expect deprecation warnings (pre-ARC, possibly `NSOpenGL`) and needs arm64 | **port** (moderate) |
| UIKit | `gui/cg`, `player_iphone` | current, but a 2010-era iOS app needs a lot of modernisation | **port**, low priority |
| Direct2D + DirectShow | `gui/d2`, `player_mfc` | Direct2D still current; DirectShow legacy but present; MFC still ships | **ok-ish** |
| pthreads | `lib/unix`, players | fine | **ok** |

## Toolchains and build systems

| Item | Status | Rating |
|------|--------|--------|
| autotools (`configure.ac`) | still works in principle; ~1,100 lines of configure logic with many dead options (npambulant, gstreamer 0.10, macfat/universalsdk) | **port** (prune), or replace with CMake/Meson later |
| Xcode 4.3 projects | modern Xcode will probably still open them, but with i386/x86_64-only archs, old deployment targets and libstdc++ references | **port** |
| VS2010 projects | VS can upgrade them | **port** |
| Android project | an SDL-era Android build of 2013–2014; the Android toolchain has changed completely since | **port**, low priority |
| `build-third-party-packages.py` | hard-coded URLs from 2014 (some `ftp://`, some mirrors), Python 2 | **replace**: use system packages (Homebrew, apt, vcpkg) |
| C++ dialect | pre-C++11 code. Very few hard breaks found (1 `auto_ptr`, in config headers; no `register`, no dynamic exception specs). Expect a lot of warnings, not many errors *(guess)* | **ok-ish** |

## Overall picture (cold, before any build attempt)

- The **platform-independent core** (`lib`, `common`, `smil2`, the non-ffmpeg
  part of `net`: about 25k lines) has few external dependencies besides
  expat and pthreads. It's probably the easiest part to revive, and the most
  valuable: a complete SMIL 3.0 timing engine.
- The `gui/none` back-end, plus the trace output from `trace_player` /
  `pyamplugin_trace`, suggests a cheap first milestone: **build libambulant
  headless and play a document with no rendering at all, comparing the
  timing trace against `tests/nightly/*-reference.txt`**. That checks the
  SMIL engine without touching ffmpeg, GUI toolkits or Python. There's no
  stand-alone headless driver today: `gui::none` is only used as a fallback
  inside the real players and pyambulant *(code)*, and the reference traces
  were generated through the Python plugin. So a small command-line driver
  (~200 lines, modelled on a `mainloop`) would have to be written.
- Second milestone: ffmpeg port + SDL2 player on Linux and macOS (one
  renderer that works on both).
- Third: the native macOS (`cg`) player. Windows and iOS after that, if at all.
- **Drop outright:** npambulant, ieambulant, gstreamer 0.10, the
  xulrunner/Carbon bits, and the Xcode/VS project files that only build
  those.
